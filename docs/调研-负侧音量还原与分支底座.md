## 1. 问题 2：分支红石线下方缺底座 —— **已修复**

### 根因

[index.html](../../index.html) 分支放置循环只写了信号层的红石粉，没写底座：

```js
for (let z = zc + step; z !== zEnd + step; z += step) {
  W(xCur + 1, ySig, z, 'minecraft:redstone_wire');   // ← 只有这一行
  stats.wires++;
}
```

主位（`zc`）与末端盒（`zEnd`）都有 `W(..., yb, ..., 'minecraft:snow_block')`，唯独中间的分支格悬空。

### 修复

```js
for (let z = zc + step; z !== zEnd + step; z += step) {
  W(xCur + 1, ySig, z, 'minecraft:redstone_wire');
  W(xCur + 1, yb, z, 'minecraft:snow_block');   // 整条分支统一托底
  stats.wires++;
}
```

### 验证

新增 `validate W`：构造 v=100 + v=60 的双音场景，遍历网格检查**每一格**红石粉下方是否有方块。修复前 12 格悬空，修复后 0 格。

## 2. 问题 3：车道徽章不报音高越界 —— **已修复**

### 根因

`laneConflictStats` 只统计「同 tick 超 3 位」：

```js
for (const c of merged.values()) {
  if (c > 3) { overflowTicks++; discarded += c - 3; }
}
return { maxSimul, overflowTicks, discarded };   // ← 没有任何 key 检查
```

但生成端把两类丢弃合并计数（[index.html](../../index.html)）：

```js
warns.push(`丢弃了 ${stats.notesDiscarded} 个音符（车道内同 tick 超过 3 个音符盒位、或音高超出音符盒音域 key 33-57）...`);
```

→ 徽章显示「✓ 无冲突」，生成却报 757 个丢弃。**两条信息源不一致。**

### 修复

1. `laneConflictStats` 增加 `outOfRange` 计数（遍历 `layer.notes` 检查 `key < 33 || key > 57`）
2. 新增 `laneConflictBadge(stats)` 统一生成文案，**两处渲染共用**（此前是复制的两份代码，容易再漂移）
3. 徽章现在分别报出两类：`⚠ 预计丢弃：N 音符同 tick 超 3 位；M 音符音高越界（key 需在 33–57）`

### 验证

新增 `validate X`（两类同时出现）+ `X2`（无问题时仍显示「✓ 无冲突」）。

## 3. 问题 1：负侧小 velocity 方向 —— **调研中，需要你的数据**

### 已排除的可能

我按你的条件（anchor = −24、主要 velocity = 80）跑了完整链路诊断，**所有组合下方向都是正确的**：

| velocity 组合 | zLine（主链） | v=100 的盒 | v=80 的盒 | v=127 的盒 |
|---|---|---|---|---|
| 全 80 | **−29** | −24 | −29（主位） | — |
| 100 + 80 | **−24** | −24 | **−29** | — |
| 127 + 80 | **−18** | −24 | **−29** | −18 |
| 127+100+80 | **−24** | −24 | **−29** | −18 |
| 80 为主 + 少量 100 | **−24** | −24 | **−29** | — |

**关键观察**：`v=80` 的盒**恒在 −29**（比 −24 更负 = 更远 = 更轻），`v=100` 恒在 −24。方向符合物理语义。

同时确认：负侧分支**在物理上不可能**产生 z > −24 的盒——`zOffMin/zOffMax` 与 `Math.min(zLine, -2)` 双重约束保证所有负侧盒 `z ≤ −1`。

### 剩余三种可能

**可能 A：你看的「原位」其实是主链位置，不是锚点。**
上表第一行：全 80 时主链被重定位到 −29，`v=80` 的盒就在主链（dz=0），`v=100` 的盒在 −24。如果你把 −29 附近当成「原位」，就会觉得 v=100 反而更靠里。

**可能 B：车道起点被让位平移了，实际 anchor 不是 −24。**
`c.volAnchorZc = c.zc` 取的是**让位后**的值。若轨道 0 在 z=0（默认），且**任何**车道 `|zc| ≤ 1`，会触发全局平移 `shift = max(0, 2 − minZc)`。你拖到 −24 的车道会被一起推走——如果 minZc 就是你这条 −24，shift = 26，anchor 变成 **+2**。

**可能 C：你看到的是另一条车道。**
声音还原是每条车道独立 opt-in。若有多条车道开了，容易看错。

### 需要你提供（三选一，任选其一即可定位）

1. **截图**：游戏内看到问题的那段，标出两个盒的坐标
2. **调试包**：点「导出 JSON 调试包」，把 `geometry.volRestore` 与 `stats.discardedDetails` 发我
3. **文字描述**：
   - 那条车道在车道池里显示的**起点 Z 是多少**？
   - 看到的「小音量盒」比「v=100 盒」是**更靠左**还是**更靠右**？
   - 生成明细里有没有「矿车行走行让位」这条？

### 无条件可做的加固

无论问题 1 的结论是什么，下面两条都值得做：

1. **`volRestoreEntries` 增加 `effectiveZc`（让位+重定位后的实际主链 z）** —— 现在的 `zLine` 就是这个值，但语义不清晰，容易和用户拖的 `start.dz` 混淆。文档与 UI 提示都要说明「实际位置 ≠ 起点栏的数值」。
2. **负侧断言加固**：在 `validate` 里加一条「负侧任何盒 `z ≥ 0` 即失败」的网格级检查（现在只有 `N5a` 检查了盒 ≥1 的下界，没检查负侧的上界）。
