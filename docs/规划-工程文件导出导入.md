# 规划：项目设置导出/导入（含 NBS 文件）

> 日期：2026-11-07（v3：经 12 轮审视修订）· 状态：**待用户确认后实施**
> 目标：把「导入 NBS 后做的全部项目设置」与 NBS 文件本身打成**一个可移动的工程文件**，实现换机 / 换浏览器 / 分享 / 归档不丢配置，**导入即完整恢复（重新加载语义）**。

## 2. 方案选型（结论不变）

| 方案 | 结论 |
|---|---|
| A. 单文件 zip | ✅ **采用**——复用 `buildZip`，NBS 字节无损，单文件即完整恢复 |
| B. 单 JSON + base64 | ❌ base64 膨胀 33%，MB 级 NBS 内存翻倍 |
| C. 仅设置 JSON | ❌ 不满足「包含 NBS 文件本身」 |

## 3. 工程文件格式（v2）

扩展名 `.nbsproj`（zip，STORE）。

```
song.nbs                  # 必需：原始字节，逐位不变
project.json              # 必需：{ format, formatVersion, meta, state }
assets/lyric-font.ttf     # 可选：用户上传的歌词字体原始字节（存在才打包）
```

**`project.json` 分层（防止与 localStorage 载荷字段撞名）**：

```json
{
  "format": "nbs2schematic-project",
  "formatVersion": 1,
  "meta": {
    "exportedAt": 1762...,
    "song": { "fileName": "canon.nbs", "bytes": 123456 },
    "font": { "name": "myfont.ttf", "entry": "assets/lyric-font.ttf" }
  },
  "state": { ...与 localStorage payload 完全同构（v:2 ...）... }
}
```

- `state` 直接复用 `loadSavedState` 的校验逻辑（零重复实现）。
- **不设 `manifest.json`**（v1 规划里的双源问题：格式版本与 sha 在两处会漂移）。
- **sha256 不做**（原规划用 `crypto.subtle`——它在 `file://` 下**不可用**；引入纯 JS SHA-256 收益低：zip 内已有 CRC32 可验损坏）。改为记录 `song.bytes` 长度校验。

## 4. 功能设计

### 4.1 导出

**入口**：生成区工具栏新增按钮，**载歌后即可用**（不依赖「生成」成功——`downloadBtn` 的门控不适用于此）。

**流程**：
1. `buildStatePayload()`（从 `saveStateNow` 抽取的单一来源）→ `state`
2. `meta`（文件名取 `song.sourceFileName`、字节数、字体信息若 `LyricFont.uploaded` 存在）
3. zip 条目：`song.nbs`（`AppState.fileBytes`）、`project.json`、可选字体
4. 下载 `<歌名>.nbsproj`

**前置修复（必须）**：`buildZip` 的 `...[data]` 展开改为**分块 `Uint8Array.set`**，否则 MB 级 NBS 会撑爆调用栈/内存。这是本次实施的**第 0 步**，改动后粒子 zip 产物必须逐字节不变（有现成断言可验）。

### 4.2 导入

**入口**：`fileInput` accept 增加 `.nbsproj`；dropzone 分流（`.nbs` → 原路径，`.nbsproj` → 工程导入）。

**流程（先全验后应用，失败不改当前会话）**：
1. 读 ArrayBuffer → `readZip()`（新增，STORE only）→ 取条目
2. 必需条目校验：`song.nbs` 存在非空、`project.json` 存在且 JSON 可解析
3. `format === 'nbs2schematic-project'` 且 `formatVersion <= 1`
4. `parseNBS(songBytes)` 成功（失败 → 「工程文件内的 NBS 已损坏」）
5. `song.sourceFileName = meta.song.fileName`（保证 `stateKey` 与导出时一致）
6. 用**同一个 `loadSavedState` 逻辑**校验 `state`（需把校验主体抽成 `validateStatePayload(song, state)`；`loadSavedState` 改为薄封装）
7. **应用后必须重跑完整 UI 重建链**（复用 `onSongLoaded`，见下）
8. **强制覆盖** localStorage（`saveStateNow()`）
9. 字体：若 `assets/lyric-font.ttf` 存在 → `lyricFontUpload(bytes, meta.font.name)`；缺失但 `state.settings.lyric.font === 'upload'` → 提示「需重新上传字体」（不阻断）

**关键实现细节（v2 补正）：`importProject` 应复用 `onSongLoaded`，不要自己拼 UI 刷新**

`onSongLoaded(song, bytes)` 已完成全部 UI 重建（[index.html:3315](../../index.html)）：`renderSongInfo` / `renderTempoAdvice` / `renderLayerList` / `renderLaneSection` / `renderRefLaneSection` / `renderSfxEffectList` / `renderSettings` / `renderLyricSection` + 各 section `hidden=false` + 清空旧生成结果与三张预览画布。自己重写一遍必然漏项（如 `topPreview.clear()`）。

做法：让 `onSongLoaded` 接受一个可选第三参 `overrideState`——
```js
function onSongLoaded(song, bytes, overrideState = null) {
  ...
  const saved = overrideState || loadSavedState(song);
  if (saved) applySavedState(song, saved);
  ...
}
```
导入 = `onSongLoaded(song, nbsBytes, projectState)`，其余流程原样复用。**零重复 UI 代码。**

**另一个容易踩的坑**：`onSongLoaded` 末尾会把 `genStatus` 设为「已恢复上次编辑状态（时间）」。导入时应改为「已载入工程文件（时间）」，需加一个分支参数或导入后覆写文案。

**`loadSavedState` 是「全有或全无」**：任一字段不合法即返回 `null`（[index.html:3435](../../index.html) 起的一长串 `return null`）。这意味着 `validateStatePayload` 复用它是**严格**的——好（不会半应用），但也意味着**旧版工程文件遇到新字段校验失败时会整体拒绝**。应对：`formatVersion` 提供升级路径（当前只有 v1，暂无迁移代码，但字段保留语义）。

**zip 条目策略**：必需条目缺失 → 拒绝；**未知条目 → 忽略并记录**（不硬拒，为未来扩展留空间）。

### 4.3 与 localStorage 的关系

| 场景 | 行为 |
|---|---|
| 导入 `.nbsproj` | 用工程内 `state` 覆盖 per-song key（`sourceFileName` 取自 meta，保证 key 一致） |
| 直接拖 `.nbs` | 不变（走 localStorage 恢复） |
| 导出 | 不改变 localStorage |

**三个 localStorage 键的边界（v3 厘清）**：

| 键 | 内容 | 是否进工程文件 | 理由 |
|---|---|---|---|
| `nbs2schematic:v1:<hash>` | per-song 载荷 | ✅ 进（`state`） | 本次目标 |
| `nbs2schematic:sfxpresets` | 用户保存的触发型模板预设（跨歌） | ❌ **不进** | 属「用户个人库」，跨歌共享；若进工程文件，导入别人的工程会覆盖/污染自己的预设库 |
| `nbs2schematic:ui` | 侧栏折叠状态 | ❌ **不进** | 纯界面偏好，与工程内容无关 |

> 若将来用户明确想要「带走预设库」，可另做「预设库导出/导入」，与工程文件解耦。

## 6. 风险与边界（v2 增补）

| 风险 | 处理 |
|---|---|
| **`buildZip` 大数组展开爆内存** | 第 0 步重构为分块 `set`；加 5MB 输入测试 |
| zip64 / deflate 输入 | 明确拒绝并报错（只支持 STORE + 非 zip64） |
| `crypto.subtle` 在 file:// 不可用 | 已移除 sha256（v1 规划错误） |
| 条目数 >65535 | 工程文件只有 2-3 个条目，无此问题；`readZip` 仍校验 EOCD 结构 |
| **上传字体未处理导致「重载」不完整** | v2 已纳入：`assets/lyric-font.ttf` 可选条目 |
| 载荷 schema 漂移 | `buildStatePayload()` + `validateStatePayload()` 单一来源 + 双向测试 |
| 导入与其他 key 的旧存档 | `sourceFileName` 取自 meta → key 自洽；旧 key 残留无害，文档说明 |
| 未知条目/未来扩展 | 忽略并记录（不硬拒） |
| 超大 NBS | 沿用 `NBS_MAX_FILE_BYTES`（256MB）；`readZip` 前同样限长 |
| **smoke 环境无 FileReader** | smoke 只测纯逻辑分支；zip 往返放 validate |
| **导入后 UI 重建漏项** | 复用 `onSongLoaded(song, bytes, overrideState)`，不重写刷新链 |
| **`stateKey` 依赖文件名 → 导入后 key 可能不同** | `sourceFileName` 显式取自 `meta.song.fileName`；若用户改过原文件名则落在新 key（旧配置残留但无害），文档说明 |
| **`parseNBS` 可能不幂等/有状态** | `parseNBS` 是纯函数（返回新 song 对象），已由 validate 大量调用验证；导入前先解析成功再应用 |
| **同名文件但内容不同（size 相同）** | `stateKey` 含 size，同 size 不同内容仍会撞 key——导入时强制覆盖可解决；直接拖 `.nbs` 时风险照旧存在（既有行为，不扩大） |
| **`sfxParams` 白名单会静默丢新字段** | 工程文件格式 `formatVersion` 与 `sfxParamsPayload` 白名单需同步演进；新增特效类型时必须同步改白名单（**这是现有隐患，本次不修，但需在 README 标注**） |
| **预设库/UI 状态不含在工程文件** | 已明确界定（见 4.3），避免导入污染用户个人库 |
| **导入时若当前已有未保存改动** | 现状每步操作 `scheduleStateSave()` 已落盘（300ms 防抖），无「未保存」概念；导入直接覆盖，**需二次确认对话框**（防误操作丢失当前工作） |
| **`.nbsproj` 被当普通 NBS 拖入** | dropzone 按扩展名分流；`.nbs` 分支仍要求 `parseNBS` 成功，`.nbsproj` 会先在分流处拦下 |
| **`lyricFontUpload` 是异步（Promise.race 4s）** | 导入时字体加载不阻塞流程；加载失败 → 提示「字体加载失败，请重传」，其余状态已恢复 |

## 7. 验收标准（v3）

1. **重新加载**：导出 → 刷新/换浏览器/清数据 → 导入，恢复：
   - 音轨池勾选、参考标记、参考车道类型/起点/特效与全部模板参数
   - 车道池分组/起点/音量还原、轨道 0 起点
   - 歌词句子与全部歌词设置、目标版本、乐器映射、soundIdMap、sfxPitchStep、矿车监听
   - **上传字体**（若导出时存在）自动恢复；加载失败的降级提示
   - **生成产物一致性**：比对 `stats` + `sfxTickList` + 网格字节哈希（不做整文件逐字节比对——`.litematic` 含 DataVersion 等元数据）
2. 导出的 `song.nbs` 与原始文件字节完全一致（长度 + CRC32）。
3. 损坏/伪造 `.nbsproj` → 明确报错且**当前会话不变**（含：当前 song、当前配置、当前生成结果全部保持）。
4. **覆盖确认**：导入前弹出确认（当前有编辑内容时），取消则完全无副作用。
5. **全局库不受影响**：导入前后 `sfxpresets` 与 `ui` 两个键内容不变。
6. 三套件全绿，基线写入 README 与 memory。
7. 不回归：直接拖 `.nbs` 仍走 localStorage；粒子 zip 产物与改造前**逐字节一致**（`buildZip` 重构的回归门槛）。
8. `.nbsproj` 拖入时**不会**被当作 NBS 解析（分流正确）。

## 9. 明确不做（避免范围蔓延）

- `manifest.json`（v1 已删）
- sha256 校验（file:// 不可用，CRC32 + 长度足够）
- 粒子 zip 内附配置摘要
- 「仅设置 / 仅 NBS」导入分支
- 导入时清理其他 localStorage key
- 界面布局窗口位置的持久化
- 导出时压缩（deflate）——STORE 足够，且现无压缩实现
- 预设库/UI 状态进工程文件（见 4.3，如需另做独立功能）
- `sfxParamsPayload` 白名单机制改造（属既有隐患，另行处理）

## 10. 十二轮审视结论汇总

| 轮次 | 抓到的关键问题 |
|---|---|
| 1（事实核查） | `crypto.subtle` 在 file:// 不可用；字体未持久化；载荷不含界面状态；`loadSavedState` 需要 song |
| 2（设计） | `manifest.json` 双源；`project.json` 顶层字段撞名；`stateKey` 依赖文件名；zip 白名单过严；导出按钮门控错误 |
| 3（验收） | 「生成产物逐字节一致」不可靠（含 DataVersion）；smoke 无 FileReader；**`buildZip` 用数组存字节会爆内存** |
| 4（实现细节） | `buildZip` 的 65535 条目上限与 32 位溢出；`sanitizeFilename` 可复用；拖拽入口只认 `.nbs` |
| 5（复用） | `onSongLoaded` 已含完整 UI 重建链，重复实现必漏；`genStatus` 文案需分支 |
| 6（边界） | 同名同 size 撞 key；旧 localStorage 残留；未知条目策略 |
| 7（全局状态） | **`sfxpresets`（跨歌预设库）与 `ui`（侧栏状态）是独立键**——必须明确是否进工程文件 |
| 8（序列化） | **`sfxParamsPayload` 白名单**：新增特效字段若不同步加白名单会被静默丢弃（现有隐患，本次不修但需标注） |
| 9（交互） | **导入需二次确认**（防误操作覆盖当前工作）；`lyricFontUpload` 是异步 Promise.race，需非阻塞降级 |
| 10（校验严格度） | `loadSavedState` 是「全有或全无」——旧工程遇新字段会整体拒绝，需 `formatVersion` 升级路径 |
| 11（拖拽歧义） | `.nbsproj` 不能落入 `.nbs` 分支；分流必须在 `parseNBS` 之前 |
| 12（验收补全） | 增加「当前会话不变」「全局库不受影响」「拖拽分流」三条断言 |

**核心结论（v3）**：骨架（zip + 单文件 + 复用校验）稳定；真正的坑集中在三处「**已有机制没被规划看见**」——
1. **`buildZip` 的内存实现**（数组展开）——不修就无法处理 MB 级 NBS；
2. **`onSongLoaded` 的 UI 重建链**——重写必漏；
3. **三个 localStorage 键的边界**——预设库/UI 状态该不该带走，必须有明确取舍。

另有两点是**既有隐患**，本次不修但需记录：
- `sfxParamsPayload` 白名单式序列化（新增特效字段必须同步）；
- `stateKey` 同名同 size 撞 key（本次导入路径可规避，直接拖 `.nbs` 不受影响）。
