## 3. 失败模式分析（738 条 FAIL 归因）

### 3.1 测试基建自身的 bug（占相当比例，前 3 周高发）
- vm 沙箱缺全局（`isInteger is not defined`）、DOM 桩 `click()` 是 noop 须用
  `dispatch('click')`、`Identifier 已声明`（重复 const）、`document.body.removeChild` 桩缺失。
- **教训**：测试桩是独立子系统，有自己的 bug；桩全绿 ≠ 真实浏览器正确。

### 3.2 AI 算错期望值（反复出现，且都是数学/计数类）
- 连接线 P=56/step=1/55（实为 51/1/50 量级）、漂移速度 0.01（实为 0.1）、
  CB 数 2（实为 1）、音高 17 误当 12、蜂蜜块 49≠48、zOff=15（实为 12）。
- **教训**：测试期望值必须由独立推导（公式手算/脚本算）而非"感觉"；
  记忆文件里专门留了"⚠ 曾误算"标注防止下次再算错。

### 3.3 桩环境复现不了的时序 bug
- 拖拽死锁：pointerdown 后车道被删 → `starts()` 变短 → pointermove 首行即抛
  `Cannot read kind`，两个窗口同时僵死。**桩里 pointer 序列全绿**。
- 解法：向用户要 DevTools console 导出日志（`-1788779665557.log`），行号+调用栈直接定位。
- **教训**：真实浏览器时序 bug 的最短路径 = 用户日志，不是本地复现。

### 3.4 环境/平台坑
- Windows：`C:\tmp` 不存在（bash 风格 `/c/…` 混用）、短路径 `YUXIAO~1`、GBK/UTF-8 乱码、
  PowerShell 命名管道 EPERM（EPERM 在受限沙箱下 Expand-Archive 失败）。
- 网络：GitHub API 拉源码（jsdelivr 拉 Litematica 源码验证读取逻辑）。

### 3.5 只有游戏内才能发现的错（测试永远测不到的层）
1. **速度模型差一倍**：网页推 tickrate=17，实际要 34——音符盒传导 0 延迟是游戏内实测值，
   wiki 查不到逐组件刻数表。
2. **MIDI 连接线段方向错**：B 端不随时间前移 → 线段平行 Z、垂直于链传播方向。
   视觉正确性只有眼睛能判定。
3. **总线各轨启动速度不一致**（启动几何残留）。
4. snare 沙子方块掉落。

**教训**：单元测试守住"产物结构正确"，游戏内实测守住"行为正确"。两者缺一不可，
且用户实测永远是最终仲裁（"若日后用户换环境测出不同，以用户实测为准"）。

## 4. 用户协作模式画像

1. **短确认驱动**：大量"ok / 是 / 不是 / 让我重新选择一下"，用户不写长篇说明，
   用最短回答裁决 AI 给出的选项（AskUserQuestion 55 次）。
2. **游戏内实测是主要输入源**：用户拿真游戏、真 Litematica 模组当验证器，
   反馈形态 = 现象描述 + 截图/日志路径（37 条实测反馈）。
3. **先问答后动手**：开局"通过问答的方式构建计划"；大改动前 AI 必须先给选项
   （用户会打断："和我对话确认修改目标"）。
4. **做减法的品味**：三次重大删除（骑猪装置、总线/触发区、延迟垫片）都是用户
   看着游戏内效果拍板"这部分我不要了"。抽象不是设计出来的，是删出来的。
5. **风格偏好明确**：雪块白轨 + 小节蜂蜜块、赭黄蛙灯每 32 格、1 档中继器、
   中文 UI、单文件零依赖。
6. **打断权**：用户随时 `[Request interrupted]` 纠正方向（文件里留有大量中断标记）。

## 5. 沉淀下来的关键机制（必须保留的资产）

1. **五套件测试基线**：verify-m1（解析器）/ validate（NBT 逐格 e2e + 10 版本矩阵 +
   SFX 场景 A~N）/ smoke-ui（~250 断言）/ gen-example（3 份样例回归）/ brace-scan。
   每个特性落地 = 代码 + 同轮补测试 + README 同步 + 记忆文件更新，四件套缺一不可。
2. **回归样本库**：`synth_*.nbs` 合成样本，每个边界行为一个样本
   （chord 31/33 tick 边界、vanish、bg 3/4 拍号……），NBS 格式知识全部实锤过
   （v6 仅 first_custom_index 16→20；notes = tick_delta 后跟 layer_delta 到 0，
   每(声道,tick)至多 1 音）。
3. **记忆分层**：MEMORY.md 索引 → 12 个主题文件，每个文件带"当前语义 + 历史层"
   两段结构，新段推翻旧段时显式标注"与上文冲突以本段为准"。
   这是对抗 40 次压缩失真的核心机制。
4. **冻结字符串纪律**：particleex 命令文本逐字冻结（用户自定模组命令，只允许
   替换坐标段/寿命/组名槽位）——"AI 不要顺手修用户的代码"原则。
5. **提交纪律**：一次逻辑改动一个提交、中文提交信息（标题=功能+关键数值+测试基线，
   信息密度极高）、无 Co-Authored-By、`.git_commit_msg.txt` 机制。
6. **验证三通道**：wiki 查格式 → 本地 jar/模组源码实锤 → 用户游戏内实测。
   （ochre_froglight 查 1.21.11 jar；Litematica 读取逻辑读 fork 源码。）

## 7. 一句话总结

这个项目是"短确认 + 游戏内实测 + 做减法"的产物：**用户拿真游戏当验证器，
AI 拿五套件当护栏，记忆文件当长期记忆**；40 次压缩没有压垮项目，靠的就是
"决策写进文件而不是留在对话里"这一条纪律。
